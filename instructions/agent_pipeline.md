# Архитектура и Пайплайн Агента MarmAI

В данном документе описана сквозная архитектура, функциональная схема и пошаговые процессы обработки контекста в ИИ-агенте **MarmAI**. Система построена на базе микросервисов в Docker и разделяет быстрые задачи автодополнения кода и тяжелые аналитические задачи чата.

---

## 🔄 Пошаговое описание процессов (Data Flow)

### Сценарий А. Фоновая работа и Автодополнение (Каждые 100–300 мс)
Этот цикл работает непрерывно и незаметно для разработчика, обеспечивая максимальную скорость отклика IDE.

1. **Сбор метрик и фокуса:** Пока разработчик пишет код, плагин IDE отправляет события (открыл файл, перевел курсор, сохранил изменения) на эндпоинт FastAPI. FastAPI, используя Pydantic-схему `FileActivityCreate`, моментально отвечает клиенту `200 OK`, а саму запись асинхронно уводит в `BackgroundTasks`, сохраняя в **InfluxDB 3.0** (`file_activity`).
2. **Запрос на дополнение:** Как только разработчик останавливается на долю секунды, IDE делает запрос на `POST /autocomplete`, передавая код *до* курсора (prefix) и *после* курсора (suffix).
3. **Обогащение контекста:** FastAPI мгновенно запрашивает **Dragonfly** (Redis-совместимый кэш), откуда берется быстрая информация о технологическом стеке проекта (например, что используются `FastAPI` и `InfluxDB`).
4. **FIM-генерация:** FastAPI собирает **FIM-промпт (Fill-in-the-Middle)**:
   ```text
   <|fim_prefix|> {Код до курсора + Краткий контекст из Dragonfly} <|fim_suffix|> {Код после курсора} <|fim_middle|>
   ```
   Промпт отправляется в контейнер `ollama-qwen`. **Qwen 2.5 Coder (1.5B)** за 100-200 мс генерирует строку-дополнение и возвращает её в IDE.

---

### Сценарий Б. Сложный анализ и диалог в чате (LangGraph + Llama 3.1)
Этот цикл включается по требованию, когда пользователь выделяет код и пишет в чате: *«Оптимизируй этот метод и проверь правила безопасности»*.

* **Шаг 1. Сборка Личности (Узел Инициализации графа):**
  FastAPI делает SQL-запрос `SELECT` к **InfluxDB 3.0**, вытаскивает слои личности котика-SRE из таблицы `agent_configuration` согласно их `priority_level` (от `1_base` до `4_mood`). Формируется иерархический системный промпт с XML-тегами (`<CORE_BASE_RULES>`, `<BEHAVIOR_AND_TONE>`).
* **Шаг 2. Векторный контекст (Узел Извлечения RAG):**
  Сервис обращается к **LlamaIndex**, который производит поиск по векторной базе проекта и находит смежные интерфейсы, конфигурации или файлы моделей, релевантные запросу пользователя.
* **Шаг 3. Поднятие истории (Узел Истории диалога):**
  Из **Dragonfly** извлекаются последние сообщения текущей сессии чата, чтобы агент удерживал контекст беседы.
* **Шаг 4. Рассуждение (Узел Мышления):**
  Агрегированный пакет данных передается в контейнер `ollama-llama`. **Llama 3.1 (8B)** производит вычисления и генерирует аналитический ответ или Git-дифф изменений.
* **Шаг 5. Аудит (Узел Телеметрии):**
  Количество сожженных токенов (`prompt_tokens`, `completion_tokens`) и задержка ответа (`latency_ms`) асинхронно записываются в таблицу `agent_telemetry` в **InfluxDB 3.0** для последующего анализа производительности ИИ.

## 💾 Распределение слоев памяти по технологиям

| Технологический стек | Роль в архитектуре памяти | Хранимая информация |
| :--- | :--- | :--- |
| **Dragonfly** | *In-Memory Кэш и Стейт* | История чата текущей сессии, активный буфер файла, метаданные открытого проекта. |
| **InfluxDB 3.0** | *Долговременная хронологическая БД* | Слои личности агента (`agent_configuration`), история активности IDE (`file_activity`), Git-коммиты (`vcs_history`), телеметрия шагов LLM (`agent_telemetry`). |
| **LlamaIndex** | *Семантический RAG-слой* | Векторные эмбеддинги исходного кода проекта, абстрактные синтаксические деревья (AST). |
